# Правило проекта: настройка через сцены и инспектор Godot

Этот документ — **обязательная инструкция для будущих агентов и людей**,
которые дописывают Rally. Короткая версия: визуальные эффекты и настройки,
которые удобно выбирать глазами, живут **на узлах сцены** с `@tool`-скриптами
и готовыми пресетами. Общие данные и пресеты могут лежать в `.tres`-ресурсах,
но код не должен прятать настройки в невидимых числах.

Подробнее о новых визуальных эффектах: [`SCENE_EFFECTS_RU.md`](SCENE_EFFECTS_RU.md).

## 1. Главное требование

Любая характеристика, которую захочется поменять при настройке игры —
скорость, размер, цвет, количество, текст, порог, шанс, время, громкость,
параметр шейдера, — должна быть **видна и редактируема в инспекторе Godot**
без правки кода и без перезапуска редактора.

Для визуальных эффектов предпочтительный путь: отдельная сцена эффекта →
`@tool`-скрипт на корневом узле → понятные пресеты → точные поля только в
режиме «Свой вид». Не складывайте новые экранные фильтры, осадки и материалы
в один общий ресурс с длинной простынёй ползунков.

Плохо (было раньше почти везде):

```gdscript
particles.amount = 1800
camera.fov = 75.0
label.text = "НА СТАРТ"
material.set_shader_parameter("wet_darken", 0.35)
```

Хорошо (сейчас так и надо делать):

```gdscript
particles.amount = fx_config().foam_amount        # RallyFxProfile
camera.fov = f().chase_fov                         # RallyCarFeelConfig
label.text = layout().start_button_text            # RallyMenuLayout
material.set_shader_parameter("wet_darken", _p("ground_wet_darken"))
```

## 2. Как это устроено

Схема одинаковая для всех подсистем:

1. **`@tool class_name`-ресурс** в `scripts/data/` — только `@export`-поля,
   сгруппированные через `@export_group`, с комментариями `##` и дефолтами,
   равными прежним «зашитым» значениям (поведение не должно меняться, пока
   ресурс не отредактировали).
2. **Файл `.tres`** в `data/` — экземпляр этого ресурса, который и правят в
   инспекторе.
3. **Экспорт в узле**: `@export var settings: RallyStageSettings = null` и
   null-safe геттер (`s_settings()`, `f()`, `fx_config()`, `theme_cfg()`,
   `layout()`), который грузит `.tres` по умолчанию, если поле пустое.
   Экспорт в сцене главнее файла: сцена может подставить свой вариант.
4. Код читает **только** поля ресурса. Никаких магических чисел в телах
   функций, никаких строк интерфейса в коде.

Почему геттеры, а не `preload`: путь по умолчанию остаётся в одном месте,
тесты и сцены могут подменить ресурс, а ресурс без файла не ломает запуск.

## 3а. Эффекты колёс — поля `RallyFxProfile`

Всё, что летит из-под колёс и оседает на кузове, настраивается в одном месте —
`data/stage/default_fx_profile.tres`. Группы полей в инспекторе:

| Группа | Что настраивает |
| --- | --- |
| `Сила и производительность` | `fx_intensity` (общая громкость эффектов, ×), `fx_update_hz`, `fx_physics_fps`, свечение пылинок `fx_sparkle_*` |
| `Следы шин` | `chunk_*`, `min/max_distance`, `flush_interval`, `soil_spacing`, `min_looseness`, `min_speed` |
| `Цвета следов и комьев` | `spray_*_color`, `gravel/wet_soil_color`, `soil_lighten`, `soil_wet_darken` |
| `Грязь и пыль на кузове` | `dirt_color`, `body_snow_color`, `body_coverage`, `body_alpha`, `body_spread`, `body_edge_softness`, `body_dirt_buildup`, `body_snow_buildup`, скорости налипания `*_dirt_rate`, `damp_*_scale`, `rain_*`, `snow_*`, `dirt_body_prefixes`, `dirt_body_skip`. У каждого покрытия свои `body_dirt_color/rate/coverage/spread/alpha` |
| `Брызги из-под колеса (общие)` | `spray_grain_radius/height/segments/rings` (вид крупинки), `spray_min_speed`, `spray_slip/wet_threshold`, `spray_dry/wet/snow_color`, `spray_direction` — общие значения для покрытий без своего профиля |
| `Дым и облака над колесом` | `foam_*`: высота, жизнь, раздувание, размер, направление, разлёт, скорость, тяжесть, плотность, надбавка на мокром, альфа, свечение, сплющенность, вращение, турбулентность, торможение, разброс жизни |
| `Комья и капли из-под колеса` | `grit_*`: жизнь, разлёт, скорость, тяжесть, размеры зерна, количество, блеск, подсветка, разброс жизни, вращение |
| `Разлёт частиц по колёсам` | `side_splay`, `spawn_outward`, `spawn_behind`, `inherit_velocity_ratio`, `wind_pull`, `steer_boost`, `handbrake_boost` |
| `Пыль из-под задних колёс` | `dust_*`: плотность, жизнь, размер, цвет, скорость, форма коробки выброса, порог скорости и пробуксовки, раздувание, завихрения, `dust_aabb`, `dust_handbrake_slip` |
| `Скользкие полосы на трассе` / `Физика грунта` | зоны сцепления, колея и накат |

Каждый профиль покрытия (`surface_fx_profiles[i]`, тип
`RallySurfaceFxProfile`) задаёт своё: цвета сухого и мокрого пятна, доли дыма и
комьев (`smoke_share`, `grit_share`), плотность цвета `particle_tint`, силу
выброса `burst_scale`, масштабы количества/жизни/разлёта/скорости/размера,
вклад скорости, пробуксовки и мокроты и три порога. Плотность между порогами
растёт плавно (`amount_ratio_for_activity`), а скорость выброса берётся из трёх
настроенных ступеней (`velocity_scale_for_level`) — облако не «дёргается».

Тот же профиль покрытия отвечает и за налёт на кузове: `body_dirt_color` —
цвет пятна, `body_dirt_rate` — скорость налипания, `body_dirt_coverage`,
`body_dirt_spread` и `body_dirt_alpha` — густота, разлёт и предел
непрозрачности относительно общих `body_*`. Поэтому гравий оставляет светлую
полупрозрачную пыль, грязь — тёмный плотный слой, трава — слабый зеленоватый
налёт, а асфальт по умолчанию не пачкает кузов. Колесо хранит цвет покрытия,
по которому ехало, и плавно перекрашивается при смене дороги.

Порядок профилей фиксирован: `gravel`, `mud`, `grass`, `snow`, `asphalt`.
Покрытие под конкретным колесом берётся из `rally_stage.surface_kind_at()`.

### Где править

Только в инспекторе Godot — в игре панели нет. Откройте
`data/stage/default_fx_profile.tres` (или поле **Fx Profile** у корня
`scenes/rally_stage.tscn`) и правьте группы прямо в инспекторе: сцена
ссылается на этот ресурс, поэтому изменения сразу видны при F5.
У покрытий (гравий, грязь, трава, снег, асфальт) свои под-ресурсы
`surface_fx_profiles` — у каждого раскрываются собственные пороги,
доли частиц и цвета.

Профиль общий на проект: правка `.tres` меняет эффекты всех трасс, кроме
тех, что задали собственный профиль в своём `@export`.

Если хочется временных экспериментов без коммита — сохраните копию `.tres`
рядом (`default_fx_profile_exp.tres`) и подставьте её в поле **Fx Profile**
сцены; закоммиченный файл при этом не тронут.

### Единицы измерения

- `*_amount` — **частиц на одно колесо**; умножается на `fx_intensity` и на
  `amount_scale` покрытия, для GPU это лишь верхняя граница пула.
- Размеры — в метрах (`foam_size` — сторона билборда, `grit_scale_*` —
  множитель к радиусу зерна `spray_grain_radius`).
- Скорости — в м/с, разлёт — в градусах, тяжесть — в м/с² (`grit_gravity`
  по умолчанию ≈ −11, реальная баллистика).
- `fx_intensity` больше 2 требует поднять `fx_physics_fps`, иначе комья
  «плывут»: симуляция считается на этой частоте.

## 4. Как добавить новый настраиваемый параметр

1. Найдите подсистему и её ресурс в таблице выше. Если подсистемы нет —
   заведите новый `@tool class_name`-ресурс в `scripts/data/` и `.tres` в
   `data/`.
2. Добавьте поле с `##`-комментарием **и дефолтом, равным текущему
   поведению**:

   ```gdscript
   @export_group("Осадки")
   ## Сколько капель рождается за секунду при полной интенсивности.
   @export_range(0.0, 3.0, 0.05) var precipitation_density: float = 1.0
   ```

3. Подключите чтение в коде через геттер (`s_settings()`, `fx_config()`, …).
4. Обновите `.tres`, чтобы значение сохранилось как настраиваемое.
5. Убедитесь, что публичное имя поля не ломает `tests/*.gd` (тесты читают
   конкретные имена — см. п. 6).

## 4а. Ассеты обстановки — сцены, а не код

Процедурный лес **не собирает меши в коде**. Каждый вид обстановки — обычная
сцена из `scenes/props/` (корень `Node3D`, начало координат на уровне земли)
плюс запись `RallyProp` в библиотеке `data/stage/default_prop_library.tres`.

Правила:

1. Новая геометрия — **сцена**, а не `CylinderMesh`/`SphereMesh`, созданный
   в `rally_stage.gd`. Сцену можно открыть, подвигать меши и поменять
   материалы; код этого не позволит.
2. Числа расстановки (вес, размер, отступ, коллизия) — поля `RallyProp`,
   а не константы в генераторе.
3. Числа раскладки (шаг, плотность, дальность) — поля `RallySceneryConfig`.
4. Сцена перед расстановкой запекается в один `ArrayMesh` (`_bake_prop_mesh`):
   по поверхности на каждый материал, меши складываются со своими
   трансформами. Дальше работает `MultiMesh` — поэтому плотность ×30 не
   означает ×30 узлов.
5. Новый пропс = новая сцена + один элемент в библиотеке. Править
   `rally_stage.gd` не нужно.
6. Текстуры пропсов лежат в `textures/environment/` и генерируются
   `tools/make_prop_textures.py`; сцены — `tools/make_prop_scenes.py`.

## 4б. Редакторские инструменты — плагины, а не меню

Правка карты не должна требовать запуска игры. Поэтому инструменты живут в
`addons/` и работают в 3D-вьюпорте редактора:

| Файл | Роль |
| --- | --- |
| `addons/rally_track_studio/plugin.cfg` + `plugin.gd` | `EditorPlugin`: панель инструментов, док, ввод из вьюпорта, `Ctrl+R`, сохранение |
| `addons/rally_track_studio/studio.gd` | состояние и правки: выбор, драг, undo, сохранение `.tres`, пересборка |
| `addons/rally_track_studio/studio_view.gd` | вся отрисовка разметки поверх вьюпорта (2D-слой, не 3D-меши) |
| `addons/rally_track_studio/dock.gd` | док «Мир трассы»: ползунки рельефа, насыпи, сцепления, тумана и экспозиции |
| `addons/rally_track_studio/studio_modes.gd` | номера режимов (трасса, полотно, лес, зоны) |
| `scripts/track/route_analysis.gd` | математика разметки: выборка, кривизна, повороты, предупреждения, профиль |

Правила для инструментов редактора те же, что и для игры:

1. **Никаких чисел в коде.** Всё оформление и пороги — поля
   `RallyTrackStudioSettings`, файл `data/editor/track_studio.tres`.
2. **Инструмент не хранит данные.** Он правит те же ресурсы, которые читает
   `RallyStage` (`RallyTrackConfig.road_curve`, `route_sections`,
   `RallySpawnLayout`, `RallyPropLibrary`) и узлы сцены (`Props`). Дублировать
   состояние в плагине нельзя: иначе редактор и игра разойдутся.
3. **Каждая правка — `EditorUndoRedoManager`.** Одно движение мыши = одна
   запись `Ctrl+Z`; методы `apply_curve_state`, `apply_sections`,
   `apply_section_state`, `apply_spawn_state`, `_attach_node`, `_detach_node`
   вызываются и кодом, и историей, поэтому обязаны быть идемпотентными.
4. **Тяжёлое — по требованию.** Пересборка мира (`rebuild_preview`) не
   запускается на каждое движение мыши: мгновенную картинку рисует 2D-слой.
   Сборка идёт по `Ctrl+R` или по таймеру `auto_rebuild`.
5. **Сохранение — часть правки.** Правленые `.tres` пишутся на диск сразу
   (`save_resources_on_commit`), иначе получается «сохранил сцену — а в игре
   старая дорога».
6. **Только редактор.** Плагин `@tool`, в игре он ничего не делает; игровые
   параметры он не читает и не меняет.
7. **Тип писать явно.** Параметры `studio` в `studio_view.gd` и `dock.gd`
   намеренно без типа (иначе цикл `preload` между `studio.gd` и
   `studio_view.gd`). Следствие: `var at := studio.project_point(...)` **не
   собирается** — движок отвечает «Cannot infer the type of "at" variable».
   Пишите `var at: Vector2 = studio.project_point(...)`. То же правило для
   обращений к полям (`studio.length` — Variant). Этот класс ошибок ловит
   `tests/test_track_studio.py`, не дожидаясь запуска редактора.

8. **Сгенерированное не живёт в сцене.** Меш земли и его коллизия создаются
   кодом (`RallyStage._ensure_terrain_parts`) с `owner == null`: иначе
   редактор вшивает сгенерированную геометрию в `.tscn` при каждом сохранении,
   и сцена этапа распухает до десятков мегабайт. Правило общее: всё, что
   пересобирается при запуске, не должно быть частью файла сцены.

9. **Отрисовка не должна стоить дороже данных.** Правила 2D-слоя студии,
   добытые лагами на ЛЕС2:
   * никаких полигонов «на сотни вершин» (`draw_colored_polygon` с длинным
     контуром) — Godot триангулирует их за O(n²), а коллинеарные вершины
     роняют триангуляцию с `Invalid polygon data`. Длинное — режется на
     выпуклые куски (`_draw_quad`, `_draw_triangle`);
   * `unproject_position()` — только после `is_position_in_frustum()`, и с
     кэшем на `(камера, route_version)`: иначе на каждое движение мыши
     проецируются все выборки трассы;
   * `_update_hover()` возвращает «изменилось ли видимое», и перерисовка
     запрашивается только по `true`;
   * интерактивные подсказки, которые ездят за курсором, — по умолчанию
     выключены (`show_cursor`, `show_ghost_point`).

Новый параметр редактора: поле с `##`-комментарием в
`RallyTrackStudioSettings` → использовать в `studio_view.gd`/`studio.gd` →
по желанию вынести в `.tres`. Новый параметр мира, который нужно крутить
ползунком: строка в `ROWS` дока `dock.gd` (диапазоны повторяют
`@export_range` ресурса) — код дока от этого не меняется.

Проверка в два слоя:

* `tests/track_studio.gd` — в редакторе/headless: математика разметки, поля
  дока против реального `RallyTrackConfig`, включённый плагин и
  `preview_in_editor` у ЛЕС2.
* `tests/test_track_studio.py` — без движка: имена полей настроек и членов
  студии, арность вызовов `RallyRouteAnalysis`, состав `ROWS` дока,
  включённость плагина. Это единственная проверка плагина там, где Godot
  недоступен.

## 5. Шейдеры

- Параметр оформляется как `uniform` с осмысленным дефолтом и
  `hint_range` там, где нужен слайдер.
- Значение по умолчанию из кода **не перетирает** художественную настройку:
  сценарий выставляет только то, что действительно зависит от геймплея или
  погоды (мокрота, снег, зоны колеи).
- Все прочие uniform'ы можно править вообще без кода: добавьте
  `RallyShaderParameter` в `ground_shader_overrides`, `road_shader_overrides`
  или `screen_shader_overrides` у `RallyStageSettings`, выберите тип
  (`kind`) и имя параметра — оно применится поверх заводских значений.
- Свои материалы можно подставить целиком: `ground_material_override` /
  `road_material_override` у сцены этапа или `ground_material` /
  `road_material` в настройках этапа. Тогда шейдер и текстуры живут в
  инспекторе материала.

## 6. Меню и UI

- Новые экраны собираются **в сцене** (`.tscn`): тексты, размеры, цвета —
  свойства узлов в инспекторе.
- Общие цвета, шрифты, отступы и стили кнопок берутся из `RallyUiTheme`;
  строки и подсказки — из `RallyMenuLayout`. Экран экспортирует
  `ui_theme` и/или `menu_layout`, чтобы можно было переопределить их сценой.
- В коде допустима только логика: что показать, когда нажали, как
  отформатировать значение. Форматирование тоже по возможности выносится в
  `RallyMenuLayout`.
- Динамически создаваемые элементы (списки трасс, чипы погоды) помечаются
  `name`, чтобы их было видно в дереве сцены, и берут размеры из темы.

## 7. Что остаётся в коде осознанно

- Имена узлов, сигналы, порядок вызовов, структура данных.
- Пути к ресурсам по умолчанию (`DEFAULT_*_PATH`) и null-safe геттеры.
- Константы, которые не имеют смысла как настройка (например, количество
  компонентов `Vector3`).
- Внутренние формулы (как считается сцепление из мокроты) — но их
  коэффициенты должны быть полями ресурса.

Если сомневаетесь — выносите в ресурс. Лишнее поле в инспекторе безвредно,
зашитое число — нет.

## 8. Проверка

- Синтаксис: `gdparse` из `gdtoolkit` (`/tmp/venv/bin/gdparse <файл>.gd`).
- Контракты: `godot --headless --path . --fixed-fps 120 --script res://tests/<тест>.gd`.
  Тесты читают публичные имена полей и методов — не переименовывайте их
  без обновления тестов.
- Откройте сцену в редакторе: у корневых узлов должен быть виден блок
  экспортов с назначенными `.tres`; в инспекторе ресурса — все группы
  параметров.
- Без движка: `python3 tools/check_project.py` — сверяет обращения к полям
  «пультов» (`cfg.поле`) с реальными полями ресурсов и проверяет, что все
  ссылки в `.tscn`/`.tres` объявлены и ведут на существующие файлы.

## 9. Чек-лист перед коммитом

- [ ] Новых «магических» чисел и строк в телах функций нет.
- [ ] Каждое новое поле имеет `##`-комментарий и дефолт, равный старому
      поведению.
- [ ] Поле сгруппировано (`@export_group`) или лежит в подходящей группе.
- [ ] `.tres` обновлён, если нужен нестандартный дефолт.
- [ ] Экспорт в сцене позволяет переопределить ресурс.
- [ ] Инструменты редактора лежат в `addons/`, их настройки — в `@tool`-ресурсе
      и `.tres`, а не в константах плагина.
- [ ] `gdparse` чистый, тесты не ссылаются на удалённые поля.
- [ ] В этом документе обновлена таблица, если появился новый ресурс.
